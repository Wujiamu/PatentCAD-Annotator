# G28 — R-004（保证快照解析的是已读的 bytes）

负责：协调者。未 commit / push。

## 缺陷

`DictPaletteWorkflow.ReadSnapshot` 分两次从磁盘取同一份内容：

```csharp
bytes = File.ReadAllBytes(dictPath);          // ① 读字节、算身份
read.DictIdentity = DictFileVisibility.Identity(bytes);
DictModel model = DictLoader.Load(dictPath);  // ② 按路径再读一遍、解析
```

两次读取之间文件被替换，就会得到「A 的身份 + B 的模型」。后续以 A 的身份做 CAS，却把 B 的条目写进 A——普通最终哈希检查看不出 A→B→A。

方法自己的 XML 注释当时已经写着「一次 `ReadAllBytes` 同时产生身份和模型，两者必然对应同一份内容」，实现没有做到。

## 改法

一行：把已读到的字节传下去，不再按路径重读。

```csharp
DictModel model = DictLoader.LoadBytes(dictPath, bytes);
```

`LoadBytes(path, byte[])` 是五版 `DictEntry.cs` 里已有的 `internal static`，`Load(path)` 本身就是 `LoadBytes(path, null)` 的薄包装；Shared 与各版 IO 在同一程序集，无需改公开 API、读写锁或新建加载框架。`Read`/`Parsed`/`Error`、合法空字典、严格 UTF-8/JSON、BOM 兼容全部不变。

## 如实记录的局限

**A→B 交错本身无法在 L1 用真实加载器确定性复现。** 它要求文件在「第一次读」与「第二次读」之间改变，单线程做不到；`ReadSnapshot` 自己会先 `ReadAllBytes`，所以在外面加独占锁只会让两次读都失败，不构成判据。

我一度写了两条试图确定性复现的测试（`G28_ModelMatchesHashedBytes_*`、`G28_ParserUsesGivenBytesNotThePath`），实测**修复前后都通过**——它们断言的是底层 `LoadBytes` 与 `Load` 的差异，而不是 `ReadSnapshot` 的行为，抓不到缺陷。已删除，没有留在仓库里充当假绿灯。

因此这一项的缺陷捕获证据是复核者的钩子探针（在证据副本内注入 BeforeParse/AfterParse，可确定性复现），生产侧证据是修复后的等价断言与 `ReadSnapshot` 语义一致。这与计划「可复用本轮探针方法」一致，也未给生产增加测试钩子。

## 残余风险

- 读取与随后的 CAD 事务之间仍有窗口（既有「原子替换 ≠ 双写锁」边界，本包不声称解决并发丢更新）。
- 三个生产调用方（改号重试、重新确认、裁决关闭后刷新）共用此入口，本轮只验证了入口本身；各调用方的行为由既有 G24/G25 矩阵守护。
