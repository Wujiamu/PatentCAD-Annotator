## 1. 基线：修复前的红灯

封存记录 `docs/test-evidence/repair-review-20261101/recovery-probe.txt` 是修复前的
组件探针结果，4 行中 2 行 FAIL：

```
FAIL|recovery_after_parse_error|valid_backup=True|retained_old_model=True|palette_snapshot_matches_disk=False|recovery_allowed=False|error=PATENTMARKER_CONTENT_CHANGED
FAIL|recovery_after_explicit_reload|current_model_null=True|valid_backup=True|button_enabled=False
```

根因（`docs/repair-work/review-20261101.md` R-034，定位 `DictPaletteControl.cs:639`、`:685`、
`DictConflict.cs:86`）：恢复入口把两件事混为一谈——

1. **“磁盘上的当前文件 + 所选备份”**（用户真正在裁决的对象）；
2. **“面板成功解析出的当前字典模型”**（可能为 null，也可能是旧缓存）。

`BtnArbitrate_Click` 用 `DictLoader.GetIdentity(_currentDict, dictPath)` 取身份。该函数只在
缓存模型引用相等且登记过身份时返回值；当前 JSON 损坏后：

- 模型仍是旧缓存（`LoadForCurrentDrawing` 解析失败时回退到旧模型），但**文件字节已变**，
  旧身份与新字节不匹配 → `ReadSelected` 返回 `PATENTMARKER_CONTENT_CHANGED`；
- 显式重载后 `_currentDict == null` → `UpdateConflictState` 里
  `pending = _currentDict != null && ...` 直接为 false → 裁决按钮禁用。

结果：**有合法备份，用户也无法恢复。** 这是一个“永远过期的快照”，不是数据保护。

### 2.1 设计要点

**身份必须来自磁盘字节，不能来自缓存模型。**
`DictConflict.CaptureSelection(dictPath, backupPath)` 直接读两个文件的字节、算 SHA-256，
并顺带记录“当前/备份是否可解析”。当前文件损坏时它**仍然返回上下文**
（`CurrentParsed = false`），这正是“从合法备份恢复”的入口。

**解析失败只影响“采用当前版本”，不影响“恢复备份”。**
- `KeepSelectedVersion`：仍要求当前内容可解析（`CurrentUnparsableError`）。把坏文件
  认定为权威内容没有意义。
- `RestoreSelectedBackup`：不看当前文件是否可解析；只看**备份**是否可解析
  （`BackupUnparsableError`），损坏备份一律拒绝且不动当前字节/属性。

**双身份 + 产品锁照旧，且只短时持锁。**
`ReadSelected` 仍是唯一的读写门禁：上下文检查 → 读两文件 → 逐个比对身份。
锁只在 `KeepSelectedVersion` / `RestoreSelectedBackup` 的动作期间持有，
**不在对话框生命周期内持有**。

**失败要说明已经发生的写入。**
`RecoveryOutcome.Wrote` 区分“什么都没做”与“字典字节已替换但基线/清理失败”。
基线失败时返回 `BaselineError` 且 `Wrote = true`，对话框文案会带上
“字典已写入，但基线更新失败；恢复点已保留”，而不是笼统的“内容已变化”。

**不让用户永远点一个过期快照。**
`UpdateConflictState` 改为 `_workflow.IsPendingConflict(dictPath)`（只看磁盘），
恢复/采用成功后 `ReloadAfterRecovery` 刷新缓存；若备份已清理则按钮自然回落。

**没有放宽严格解析。** `DictFileVisibility.DecodeText` 仍是严格 UTF-8；
坏 UTF-8 依然 `LoadBytes` 返回 null，只是不再阻断恢复。

## 4. 排除的做法（明确未采用）

| 做法 | 为什么不做 |
|---|---|
| 让 `ReadSelected` 在身份不匹配时放行 | 会破坏双身份门禁，等于放弃 G05 的写入门禁 |
| 恢复时用缓存模型的旧身份覆盖 | 正是原缺陷：把过期快照配上新文件字节 |
| 放宽 `DecodeText` 严格 UTF-8 | 会把“损坏”伪装成“合法空字典”，损坏数据会被写回 |
| 用 `_currentDict == null` 判定“无冲突” | 解析失败 ≠ 无冲突；这是按钮被禁用的直接原因 |
| 在对话框整个生命周期持锁 | 面板每 2 秒轮询，长持锁会让用户自己的 CAD 操作报 busy |
| 新增 `Strings` 键 | `Strings.cs` 不在本包文件范围；复用 `Conflict_*`/`Dict_*` 现有文案 |
| 新增 Shared 生产文件 | 需要改五个 csproj，越界；新类型放进已有允许文件 |
| 用 `dotnet test` 验证 | 本环境 VSTest 在断言前 abort（父进程句柄权限），且项目根会给出“0 tests + exit 0”的假绿 |

## 9. 残余风险

1. **`IsPendingConflict(DictModel, string)` 的形参已无用。** 语义完全由磁盘决定。
   调用方若指望“传 null 就代表无冲突”会得到相反结果。已用测试固定为
   `G16_IsPendingConflictByPath_IgnoresUnparsableCurrent`。
2. **`CaptureRecoverySelection` 会解析两次**（当前文件 + 备份），仅用于填
   `CurrentParsed`/`BackupParsed`。大字典下有额外 CPU 开销，但不持锁、不改状态。
3. **`CaptureSelection` 的 `Document` 字段需调用方填。** `DictConflict` 层不知道宿主，
   `DictPaletteWorkflow.CaptureRecoverySelection` 负责填 `RuntimeHost.ActiveDocument`；
   直接调 `DictConflict.CaptureSelection` 的话 `ContextGuard` 会拿到 null 而一律拒绝。
