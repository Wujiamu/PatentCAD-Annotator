## 失败契约

G15 给 name-first 分支加的编号左边界检查用 `InStr(1, CStr(m.Value), number, vbBinaryCompare)` 在整个匹配片段里找编号文本的**首次**出现。名称体 `G02_NAMEFIRST` 允许数字，名称本身可能含与编号相同的文本，于是首次出现落在名称内部，`NumberStartOk` 检查了错误位置，把合法条目录杀：

| 输入（空格保留） | 期望（C# `Groups[2].Index`） | 修复前 VBScript |
|---|---|---|
| `壳体X123 支架 123、` | `123` / `壳体X123 支架` | 0 命中 |
| `壳体1123 支架 123、` | `123` / `壳体1123 支架` | 0 命中 |
| `壳体AX123 支架 X123、` | `X123` / `壳体AX123 支架` | 0 命中 |

三个 C# 对照 PASS，说明缺陷只在 VBA 侧定位，不在名称语法、数值上限或 C# 实现。超长编号保护（G15 原反例 `底座123456、`）必须继续拒绝。

复现：`docs/test-evidence/repair-review-20261102/parser-vbs-full-host.txt` 的 `FAIL|display|repeat-after-letter|`、`FAIL|display|repeat-after-digit|`、`FAIL|display|repeat-prefixed-number|`。

为什么不用「起点 = `m.FirstIndex + Len(name)` 直接算绝对位置」：名称与编号之间还有 `G02_WS*` 空白，直接加会落在空白上；从该偏移起在 `m.Value` 内 `InStr` 既跳过空白又保证不回头进名称，是满足计划约束的最小写法。`InStr` 的起点参数是 1-based，故用 `Len(...) + 1`。

### 为什么起点不直接取 `m.FirstIndex + Len(name)`

名称与编号之间隔着 `G02_WS*`。若直接把 `Len(name)` 加到 `FirstIndex` 上，起点会落在空白上而不是编号上。补充验证（`G19/whitespace-gap-check.txt`，同一份临时语料分别喂给 C# 生产解析器和修复后的 VBScript 探针，两侧结果逐字一致）：

| 输入 | C# | VBScript | 说明 |
|---|---|---|---|
| `壳体X123 支架   123、`（多空格） | `123` / `壳体X123 支架` | 同左 | `InStr` 从名称末尾继续前进，跳过 3 个空格 |
| `壳体X123 支架<TAB>123、` | `123` / `壳体X123 支架` | 同左 | 跳过 Tab |
| `壳体X123 支架<U+3000>123、` | `123` / `壳体X123 支架` | 同左 | 跳过全角空格 |
| `壳体X123 支架123、`（无分隔） | `X123` / `支架123` | 同左 | 两侧一致；这是既有的第一梯队优先（`G02_P1` 编号在前先收集、第二梯队重叠丢弃），本次未改 |

这四个是临时补充用例，**没有**写进正式语料：无分隔那条的期望来自既有梯队规则而不是 R-016，把它固化进语料会混淆两个契约。它留在这里只为证明「跳过空白」这一步是对的，以及修复没有改变无分隔输入的既有结果。

## 红证据是怎么取得的（G15 记下的坑）

`tools/test-g02-parser.vbs` 自带一份 `CollectHits` 副本，它验证的是引擎语义等价，**不执行**生产 `Patterns.bas` 的 `Sub`（只从 `Patterns.bas` 解析 `G02_*` 常量文本）。所以：

- 只改生产 VBA → 探针不变红（无效红灯）。
- 只把探针指向修复前的 VBA 目录 → 仍然全绿，因为探针用的是自己的 `CollectHits`。这一条已单独留证：`G19/probe-trap-demo.txt`（修复后的探针 + 修复前的 VBA 源 = `passed=67 failed=0`）。
- **有效红灯**必须同时具备两件事：修复前的**探针副本**（`G19/red-probe/test-g02-parser.vbs`，与基线探针逐字节相同，`sha256 = d0a00898…3d5`）+ 修复前的 VBA 快照（`G19/red-source/Patterns.bas`，与基线 `Patterns.bas` 逐字节相同，`sha256 = 55d5c8c9…78f`）。

L2 的红灯不受这个坑影响：`test-g02-l2.vbs` 把 `.bas` 真实导入 Word 并调用 `BuildModel`，所以只要把 `vba-dir` 指向 `G19/red-source` 就是真实的生产前行为。

## 残余风险

- **部署副本未同步**：`vba-sync.ps1 -Check` 报 5 个 `[DRIFT]`（`PatentMarker-{2007,2010,2013,2015,2025}-deploy/vba/Patterns.bas` 仍是旧定位表达式）。按计划部署副本、dotm 由协调者统一同步；**在同步前，五套部署包与 `word-addin/PatentMarker.dotm` 仍带此缺陷**。
- **混合行尾**：见「编码检查」。不改变解析结果，但若后续要统一，需单独一轮并重跑两侧探针。
- **`m.SubMatches(0)` 与 Trim 的耦合**：本次依赖「捕获组本身不会被 Trim」这一点。`G02_NAMEFIRST` 尾部允许空格（`[\u4e00-\u9fa5A-Za-z0-9 ]*?` 是惰性的，正常不会吞尾部空格），但若将来名称模式允许尾部空白且捕获文本被裁剪，`Len(CStr(m.SubMatches(0)))` 会偏小、`InStr` 起点前移而可能重新命中名称内部。已在代码注释里写明该前提；改动名称语法时必须重跑本矩阵的 11 个 `g19-*`。
- **`InStr` 起点前移的退化上限**：即使起点前移，只要前移量小于名称长度，`InStr` 仍可能找到名称内的同文子串。当前实现的正确性来自「起点严格在名称之后」，不是来自任何容错。
- **R-021 跨引擎等价边界不变**：仍只在 ASCII 字母数字编号上实测，未新增全角数字或非 ASCII 编号用例。
- **本机 Word 16.0 64 位单环境**：L2 只证明本机 Word 16.0 的 VBA 引擎行为，未覆盖 Word 2010 / 32 位 Office / 不同宏策略。
- **`g19-mixed-order` 的名称里带空格**（`壳体X123 支架`）：这是名称模式允许的（`G02_NAMEFIRST` 含空格），与 review 的期望一致；但它也说明名称含空格的输入会整段进入 name。未改该语法。
