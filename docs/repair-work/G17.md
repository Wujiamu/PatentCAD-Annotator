## 1. 基线：修复前的红灯

封存记录 `docs/test-evidence/repair-review-20261101/rename-probe.txt` 是修复前的组件探针结果，
4 行中 2 行 FAIL：

```
FAIL|rename_retry_different_dictionary_same_new_number|expected_calls=0|actual_calls=1
FAIL|rename_chain_301_302_303|dictionary=303|pending_new=302|retry_service_calls=0
```

根因（`docs/repair-work/review-20261101.md` R-004，定位 `DictPaletteControl.cs:872`）：

待重试状态只有三个字段 ——

```csharp
private string _pendingRenameOld;
private string _pendingRenameNew;
private object _pendingRenameDocument;
```

因此 `RetryRenameInDrawing()` 只能问一个问题：“**当前**模型里还有没有新号？”

```csharp
DictEntry entry = _currentDict != null ? _workflow.FindEntry(_currentDict, _pendingRenameNew) : null;
if (entry == null || !NumberIdentity.AreEqual(entry.Number, _pendingRenameNew)) { /* 拒绝 */ }
ClearRenameRetry();
RenameLeadersInDrawing(oldNumber, newNumber);
```

两个后果正好对应两条红灯：

1. **换字典不拦**。同一图纸的字典被另一本恰好含 `302` 的字典替换后，`FindEntry` 仍然命中，
   于是对一个**从未确认过**的字典执行了改号服务。
2. **串接丢任务**。`301→302` 失败后继续把同一项改到 `303`：二次改号走的是
   “新号在模型里不存在”分支，既不更新也不拦截旧待处理操作；JSON 已到 `303`，
   待重试目标仍停在 `302`，点击重试时 `FindEntry(302)` 返回 null，调用服务 **0 次** ——
   任务永远无法完成。

`ClearRenameRetry()` 在重试前先清空状态，也让“失败后仍欠着”这件事无法与“已放弃”区分。

### 2.1 设计要点

**记录的是“哪一次操作”，不是“哪个号”。**
`PendingRenameOperation` 保存原 `Document`（引用相等）、图纸完整路径、完整字典路径、
**成功 JSON 写出的内容身份**、旧号／新号、失败信息、`Matched`/`Changed`。
身份来自 `DictFileVisibility.Identity`（写出的字节），不是缓存模型。

**首次同步就用上下文，不在对话框关闭后盲用 ActiveDocument。**
`EditSelectedEntry` 在对话框返回后用写回时的 `document` + `dictPath` + 写后身份构造
`RenameSyncContext`，再交给 `RenameLeadersInDrawing(old, new, context)`。

**实际 CAD 事务前核对磁盘身份。**
`RenameSyncContext.DescribeDrift()` 先比对文档引用，再比对当前磁盘身份；
任一不符就不调用 `DictPaletteCadService.RenameNumber`。

**拦住发生在第二次 JSON 写入之前。**
守卫在 `EditEntryDialog.ApplyAndWrite()` 里、`DictWriter.TryApplyEdit` 与 `WriteBack()`
**之前**调用，因此被拒绝时字典字节完全不变（探针实测 `bytes_unchanged=True`）。
被拒后编辑框内文本会被 `RestoreModelMutation` 还原，不会留下半改状态。

**相关性只按号段判断，不按字典路径。**
`301→302` 未完成时，再改 `302→303` 或 `301→305` 都会串接／覆盖那一步，必须拦；
同一本字典里 `777→778` 这类无关条目照常可改（否则整本字典被一个失败任务冻结）。
字典路径／内容是否仍一致属于**重试**门禁（`RenameRetryPlanner`），两件事分开。

> **已被 G21 替代（2026-11-02）**：「无关条目照常可改」这一段已被
> [G21](G21.md) 按 [repair-plan §12.4](../repair-plan.md) 收敛为「存在欠账时拦截该图纸
> **所有**后续编号变更」。原因：单槽位下无关改号的结果处理会按 Document 清空或覆盖
> 前一条欠账（封存 `palette-review-final.txt` 第 2/4/6 行）。本节其余内容（记录字段、
> 首次同步上下文、重试门禁、按图纸隔离）仍然有效。G21 §3.2 列出了被推翻的两条断言。

**字典变化时保留失败记录并要求重新确认，不拿“永久拒绝”替代重试。**
`RenameRetryPlanner.Decide` 返回四态：`WrongDocument` / `NeedsReconfirm` /
`MissingNumber` / `Ready`。前三种都**保留**记录并给出具体原因；
用户点重试即是对当前字典的显式重新确认，`PendingRenameRegistry.Rebind`
换绑新快照后仍保留原旧号／新号与失败信息。这满足“新的确认应有新快照”。

**按图纸隔离，A、B 各自失败互不覆盖。**
`PendingRenameRegistry` 以文档引用为键；`ReleaseForDrawing` 在图纸关闭时只释放该图纸的记录
（同时按图纸路径兜底清理未保存图纸的空路径情形）。

**不建持久任务队列。** 记录只活在本面板会话内，`DisposePalette` 即清空。

## 4. 排除的做法（明确未采用）

| 做法 | 为什么不做 |
|---|---|
| 把字典路径也当作“相关性”判据 | 同一字典里无关条目的改号会被一并拦住，等于用一个失败任务冻结整本字典 |
| 重试时先 `ClearRenameRetry()` 再判断 | 正是原缺陷：任务在能否执行确定之前就被清掉 |
| 字典变化后一律永久拒绝 | 计划明确要求“新的确认应有新快照”，不能拿永久拒绝替代可完成的重试 |
| 自动把 `302→303` 串接成 `301→303` | 计划明确“不猜测串接映射”；用户没确认的映射不能替他决定 |
| 复用 `DictConflict.RecoverySelection` | G16 §10 明确语义不同：一个描述裁决选择，一个描述待同步操作 |
| 新增 `Strings` 键 | `Strings.cs` 不在本包文件范围；提示放 `RenameSyncText` |
| 新建 Shared 生产文件 | 需要改五个 csproj，越界；新类型放进已在 csproj 里的 `DictPaletteSession.cs` |
| 在测试里直接调 `RenameNumber` 服务 | 计划明确要求“不只直接调用 RenameNumber 服务” |
| 用 `dotnet test` 验证 | 本机工作区根 ACL 会让 VSTest 发现 0 个测试却退出 0 |

## 9. 残余风险

1. **相关性只看号段，可能过宽或过窄。** `301→302` 未完成时，任何涉及 `301` 或 `302`
   的改号都会被拦。若用户确实想同时改两条互不相干但共号的条目，需要先放弃或完成。
   这是刻意的保守选择（宁可要求确认，也不猜测串接映射），但未在真实多条目场景验证。
2. **`PendingRenameRegistry` 以文档对象引用为键，文档对象不释放会导致记录泄漏。**
   已由 `ReleaseForDrawing` / `DisposePalette` 覆盖，但真实宿主若在未触发
   `DocumentToBeDestroyed` 的情况下丢弃文档对象，记录会留到面板销毁。
3. **`RenameSyncContext.DocumentName` 用反射读宿主 `Document.Name`。**
   五个版本的 `Document` 类型不同，反射避免把宿主类型写进共享源码；
   若某版本 `Name` 不是属性而是字段，`DrawingPathOf` 会返回空串。
   空串只影响“按路径兜底释放”，不影响文档引用判定与身份判定。
4. **`Rebind` 会覆盖 `DictPath`/`DictIdentity`，但保留 `Detail`。**
   失败信息描述的是**旧**字典上的失败；重新确认后这条信息已不代表当前字典的失败原因。
   面板文案同时给出新确认结果，但日志里的 `Detail` 与当前字典可能不一致。
5. **`DescribeDrift()` 每次重试都重新读盘算 SHA-256。** 大字典下有额外 IO，
   但与 G16 的 `CaptureSelection` 同量级，且只在用户点击时发生，不在轮询里。
6. **`EditEntryDialog` 5 参构造传 `guard = null`。** `BtnAddEntry` 走这条路径，
   新增条目没有旧号因此不需要守卫；但若将来有人从 5 参构造进入**改号**流程，
   守卫会被静默跳过。已用 6 参构造作为改号路径的规范入口。
7. **`Strings.cs` 未改，新提示走 `RenameSyncText`。** 它与 `Strings.Lang` 同步切换，
   但不在 `ApplyLanguage()` 的刷新列表里 —— 语言切换后已显示的旧文案不会立即重写。
